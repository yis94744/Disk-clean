# 04 - 修复方案审计

对 `03-修复方案文档.md` 的 F1~F8 逐项审计：方案是否对症、副作用、回归风险、结论。
审计在实施**之前**完成，实施后回填验证结果。

---

## F1 修复 P1：`self._is_broken_command` → `RegistryIssue._is_broken_command`

- **对症性**：✅ 根因就是属性归属错误，最小改动。
- **副作用**：无（纯调用修正，被调函数本身已在上一轮经过 5 组边界用例验证）。
- **回归风险**：极低。
- **审计结论**：**通过**。
- 【验证后回填】离线 `RegistryScanner().run()` 三阶段 12.7s 完成，无异常；
  GUI 扫描 20s 内出结果并检出夹具。✅

## F2 QThread.run 异常兜底

- **对症性**：✅ 直接消除"线程静默死亡 → UI 永远转圈"这一故障模式（P1 在 GUI 上表现的机制）。
- **副作用**：异常被捕获后仍 emit finished(已收集的 issues)，UI 会显示"扫描出错"而非卡死——行为正确。
- **回归风险**：低。需注意 except 中不能再抛异常（message 截断到 120 字符）。
- **审计结论**：**通过**。补充意见：其余 QThread 的统一治理（统一 BaseWorker 模式）列为后续改进，不在本轮扩大爆炸半径。
- 【验证后回填】注入异常场景：UI 收到"注册表扫描出错: ..."提示并恢复可用。✅

## F3 HKCU hive 常量

- **对症性**：✅ 0x80000000→HKCR 是确定的事实错误；改用 `winreg.HKEY_CURRENT_USER` 常量
  消除"注释与代码不一致"这类隐患再次发生的可能。
- **副作用**：启动管理列表将新增 HKCU 项（ctfmon/OneDrive/Edge 等 4+ 条）——这是修复的预期结果，
  但用户会"多看到"以前看不到的项，属于信息变完整而非破坏。
- **回归风险**：低。需确认 `_disable_selected` 对 HKCU 项写入 StartupApproved 的路径
  （harness B1 已按正确 hive 验证过写入逻辑本身）。
- **审计结论**：**通过**。
- 【验证后回填】GUI 显示 HKCU 4 项 + HKLM 3 项，desktop.ini 消失。✅

## F4 过滤 desktop.ini

- **对症性**：✅。
- **副作用**：无。极端场景：用户确实想看 desktop.ini——不是本功能的合理需求。
- **回归风险**：无。
- **审计结论**：**通过**。

## F5 类别中文映射补全

- **对症性**：✅ 映射缺失是显示层问题，补映射即可。
- **副作用**：仅影响大文件页文本；`get_file_extension_category` 返回集合核对过
  （Video/Image/Audio/Archive/Document/Code/Program/System/Font/Mobile App/Web/Net/Shortcut/Other），
  补全后 CAT_NAMES 覆盖全部返回值，不会再出现英文回退。
- **回归风险**：无。
- **审计结论**：**通过**。

## F6 安全等级标签中文化

- **对症性**：✅。
- **副作用**：`SAFETY_LABELS` 的 label 字段被 GUI 直接显示；代码中无对英文文案的字符串比较
  （已 grep 确认比较均基于 level 数值），改文案安全。
- **回归风险**：低。外部脚本若依赖英文文案会受影响——本项目无此类消费方。
- **审计结论**：**通过**。选词采用"安全/建议清理/谨慎/受保护"，与安全等级语义对应。

## F7 磁盘分析器加回导航

- **对症性**：✅ 页面类、TreeMap 控件、删除（回收站）逻辑全部存在且此前已修，
  仅缺导航入口；加回属于"恢复既有功能"而非新开发。
- **副作用**：侧边栏 10→11 项；图标为新增绘制分支，需目检观感。
- **回归风险**：低。页面懒加载机制不变；首次进入会构造 DiskAnalyzerPage（其 ScanCache
  死代码已在前轮移除，无历史包袱）。
- **审计结论**：**通过**。附加检查：`PAGE_TITLES` 同步补齐，否则标题栏显示 key。
- 【验证后回填】侧边栏出现"磁盘分析"，扫描 X: 后 TreeMap 与文件列表均正常渲染。✅

## F8 一键清理后台线程化

- **对症性**：✅ 与软件管理卸载线程化同模式（已验证的模式复用）。
- **副作用**：清理期间按钮禁用 + 状态提示；需要在 finish 槽恢复按钮并刷新汇总——
  忘记恢复按钮是本方案最大的实现风险（审计要求实现时用 try/finally 语义的 finish 槽兜底）。
- **回归风险**：中低。`engine.clean` 本身无线程依赖（纯文件/子进程操作），
  信号跨线程为 Queued 连接，安全。
- **审计结论**：**通过**，附实现要求：finish 槽必须无条件恢复按钮。
- 【验证后回填】离屏 harness：清理期间按钮禁用、结束后恢复、释放量汇总正确。✅

## 总体结论

F1~F8 全部对症、改动面可控、无数据破坏性操作；其中 F1/F3 属于"上一轮修复不完整"的
纠偏，F2 属于可靠性加固，F7/F8 属于功能恢复。批准按文档实施。
实施顺序：F1+F2（同文件）→ F3+F4（同文件）→ F5 → F6 → F7 → F8 → 统一验证。
